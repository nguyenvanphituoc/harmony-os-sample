# UC-01 — Toggle and delete, guarded by a settle window that survives a revisit

Actor: the user, on P2 List, across one or more visits (leaving and reopening the list between
them). Covers REQ-1, REQ-2, REQ-3, REQ-4, REQ-5.

## Input / Output

- Input: a tap on U1 (`list.itemCard.toggle`, `itemId`) or U2 (`list.deleteItemButton`,
  `itemId`), on a `ListViewModel` built by any visit — including one built after the visit whose
  toggle opened the window.
- Output: none observable to the caller. `ListViewModel.onToggle` / `onDeleteItem` both return
  `void`; either the underlying effect happens (`ToggleItem.execute`, `ItemDeleteOpener.
  openDelete`) or the call is a silent no-op.

## Steps

1. `TodoModule` builds one `SettleWindow` in its own constructor, once per app session
   (domain-model.md A2). Every call to `TodoModule.listViewModel(listId, clock?)`
   (`Index.ets:31`, on every navigation to P2) passes that same instance into the new
   `ListViewModel` it constructs (N4).
2. `ListViewModel` stores the window it was given (a new optional 8th constructor param). Built
   without one — every existing call site that predates this pitch — it constructs its own
   private `SettleWindow`, so behavior with no shared window is unchanged (A3, R4).
3. The user taps U1 on some visit's `ListViewModel`; `onToggle(itemId)` (N1) reads
   `this.window.isSettling(clock.now())`. **Inside the window:** the tap is ignored — no call to
   `ToggleItem.execute`, no call to `mark` (R2). **Outside the window:** `ToggleItem.execute
   (itemId)` runs, then `this.window.mark(now)` opens the window (unchanged sequencing from
   today's `onToggle`).
4. The user leaves the screen (U3, back) and reopens the same or a different list (U4). A new
   `ListViewModel` is built (step 1-2), but it is given the *same* `SettleWindow` instance the
   previous visit's `ListViewModel` wrote to in step 3 — the window's state, unlike the view
   model's, is not rebuilt.
5. The user taps U2 on the new visit's `ListViewModel`; `onDeleteItem(itemId)` (N2) reads
   `this.window.isSettling(clock.now())` on the *same* instance step 3 marked. **Inside the
   window (elapsed time since step 3's mark is under `windowMs`):** N2 returns without looking
   `itemId` up and without calling `dialogs.openDelete` — no dialog, nothing deletes, and the
   window is not written (R1). **Outside the window:** N2 looks `itemId` up and calls
   `ItemDeleteOpener.openDelete(itemId, found.title)` naming that row's item, exactly as before
   this pitch (R3).
6. A toggle tap on the new visit's `ListViewModel`, inside the same window, is guarded identically
   to step 3's "inside the window" branch — ignored, no effect (R2). Outside the window, it
   toggles exactly as before (R3).
7. Within one visit with no navigation in between, steps 3 and 5 run against the same
   `ListViewModel` and the same window instance it was given at construction — this is exactly
   toggle-once's and delete-settle's existing behavior, unchanged (R4).

## Invariants

- [INV-01] `SettleWindow`'s length stays one named constant (`SETTLE_WINDOW_MS`, 400ms); this use
  case adds no second constant.
- [INV-02] Exactly one `SettleWindow` instance exists per app session, owned by `TodoModule`, and
  is the same instance every `ListViewModel` built for the app's lifetime is given — its lifetime
  is not any `ListViewModel`'s lifetime (A2).
- [INV-03] `SettleWindow.mark` is called only from `onToggle`'s success path (after `ToggleItem.
  execute`), never from `onDeleteItem` — a delete inside the window neither opens nor extends it
  (unchanged rule, now enforced on shared state) (A2, delete-settle's INV-03 restated on the
  shared window).
- [INV-04] A `ListViewModel` built with no `SettleWindow` argument builds its own, so every
  existing unit test and call site that predates this pitch keeps its current behavior with no
  edit (A3, R4).
- [INV-05] `TodoModule.listViewModel()` still constructs a new `ListViewModel` on every call — no
  caching added, no change to view-model lifetime beyond handing it the shared window (no-go
  compliance, code-surface.md).

## Error Cases

None new. The existing "item not found" branch in `onDeleteItem` (`found === undefined` → no
dialog opens) is reached exactly as before when step 5's outside-window branch runs and the
lookup misses; a tap ignored by the window (steps 3, 5, 6 inside-window branches) is a defined
no-op, not a failure.

## System Flow

`U4 -> N4 TodoModule.listViewModel (passes shared S1) -> new ListViewModel` (repeats per visit,
same S1 each time) · `U1 -> N1 ListViewModel.onToggle -> S1.isSettling -> [inside: no-op] |
[outside: ToggleItem.execute -> S1.mark]` · `U2 -> N2 ListViewModel.onDeleteItem -> S1.isSettling
-> [inside: no-op] | [outside: item lookup -> ItemDeleteOpener.openDelete]`. `S1` (the settle
window, now `SettleWindow`) is written only by N1's success path, read by both N1 and N2, and its
own lifetime spans every N4 call in the session — this is the use case's entire fix.
