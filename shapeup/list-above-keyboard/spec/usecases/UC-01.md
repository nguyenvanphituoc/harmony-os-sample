# UC-01 — Every item stays reachable while the keyboard is up

Actor: the user, on P2 List with the new-item field (U1) focused, or on P3 the list-name dialog
(new or rename) with its field (U4) focused. Covers REQ-1, REQ-2, REQ-3, REQ-4, REQ-5.

## Input / Output

- Input: focusing U1 (raises the keyboard on P2), adding an item via U2 while the keyboard is up,
  swiping the item list (U3), or focusing U4 (raises the keyboard on P3).
- Output: none new to any repository or store — `AddItem`, `ToggleItem` and item deletion are
  called exactly as today (No-goes). The observable output is layout: which items are on screen
  and tappable, and whether the dialog stays fully visible.

## Steps

1. The user taps U1 (`list.newItemField`). The keyboard raises, as it does today. Before this
   pitch, nothing shrinks P2's content for it (domain-model.md: zero keyboard-avoid setting
   anywhere in the app) — the `List`'s `.layoutWeight(1)` resolves against the full page height and
   the list has nothing to scroll, so any item below the keyboard's top edge is unreachable. After
   this pitch, the container above the `List` (window- or page-scoped, per N1, decided at Wire/
   Build) shrinks for the keyboard, and `.layoutWeight(1)` shrinks the `List` with it — for free,
   with no change to the `List`'s own layout code (domain-model.md).
2. With the keyboard up and the list shrunk to fit above it, the user swipes the item list (U3,
   the new N2 `swipe` device step). Items that were below the keyboard's top edge, including any
   done item sunk to the bottom of the list, scroll into view and stay tappable — reachable without
   closing the keyboard (R1).
3. The user taps U2 (`list.addButton`) with the keyboard still up. `AddItem` runs exactly as today
   (unchanged domain logic; the new item lands at the top of the open items, per existing sort
   order — out of scope per the pitch's Rabbit Holes). The new item is visible, and — because
   step 1's resize is still in effect — every done item remains reachable by swiping, without the
   keyboard closing (R2).
4. With no field focused anywhere (keyboard down), P2 and P1 render exactly as they do today — the
   setting from step 1 produces no layout delta at rest; it is a keyboard-driven resize, not a
   permanent change (R3).
5. The user opens P3 (a new-list or rename dialog, from P1) and taps U4 (`listName.field`). The
   keyboard raises. The dialog — title, field, error text if present, Save/Cancel — stays fully
   visible; no part of it is covered by the keyboard, whether the setting picked in step 1 is
   window-wide (reaches P3 directly) or page-level (P3's `promptAction.openCustomDialog` overlay is
   independent of P2's container, per the spike's read of its resting position) (R4).
6. The device-check language (`scripts/ui-flow.sh`) gains a `swipe id "<node>" up|down` step (N2)
   that resolves a node by id exactly as `tap` does, then drives `hdc shell uitest uiInput swipe`
   across that node's bounds — the only step type missing before R1 and R2 can be graded on the
   emulator (R5).

## Invariants

- [INV-01] The `List`'s own component code (`space`, `.width('100%')`, `.layoutWeight(1)`,
  `.scrollBar(BarState.Off)`, the `Repeat<TodoItem>` over `ItemCard`) is unchanged — this pitch
  changes only the height its container resolves against, never the `List`'s own layout
  declaration (domain-model.md).
- [INV-02] Item order, and the add/toggle/delete domain logic (`AddItem`, `ToggleItem`, item
  deletion), are unchanged — No-goes.
- [INV-03] With no field focused, P2's and P1's layout is byte-for-byte what it is today — the
  setting from Step 1 is conditional on keyboard state, not a permanent resize (R3).
- [INV-04] P3 (both the new-list and the rename dialog — same `ListNameDialog.ets` component)
  stays fully visible with the keyboard up, independent of which candidate setting Step 1 picks
  (R4).
- [INV-05] The `swipe` device step (Step 6 / N2) resolves its target the same way `tap` and
  `doubletap` already do — by id, via the existing `find(nodes, kind, value)` lookup in
  `scripts/ui-flow.sh` — no new node-lookup mechanism (R5).

## Error Cases

None new. This pitch adds no new failure path, no new error text, no new dialog state — it changes
layout only. The Done-key-on-empty-field message (seen during the repro that motivated this pitch)
is explicitly out of scope (shaping.md Rabbit Holes).

## System Flow

`U1 -> N1 (keyboard-avoid setting, window- or page-scoped) -> P2's container shrinks -> List
.layoutWeight(1) shrinks with it (no List-side change)` · `U3 -> N2 swipe step -> hdc shell uitest
uiInput swipe -> scrolled item becomes findable/tappable` · `U2 -> AddItem (unchanged) -> new item
rendered -> still within N1's resized List` · `U4 -> keyboard raised -> P3's
promptAction.openCustomDialog overlay -> unaffected by N1 (page-level) or also covered by N1
(window-wide) -> stays visible either way (verified, not assumed, at Build)`.
