# UC-01 — MY LISTS card stays in sync with its list

Actor: the user, on P1 My Lists, across a round trip through P2 List (or the P1 rename dialog)
that changes a list's items or name. Covers REQ-1, REQ-2, REQ-3, REQ-4, REQ-5, REQ-6.

## Input / Output

- Input: U4 (back, `list.backButton`) after a P2 action that reassigns `store.items` (toggle,
  add, delete — U3), or a rename confirmed from P1's own dialog that reassigns `store.lists`.
- Output: none returned to the caller. The observable effect is what P1's already-mounted U1
  badge and card name display on the next frame after the store changes — no new return value,
  no new event.

## Steps

1. `ListsViewModel.cards` (a `@Computed` getter, domain-model.md) reads `store.lists` and
   `store.items` — both `@Trace` fields on the `@ObservedV2 TodoStore` — and returns a fresh
   `ListCard[]` on every read. This is unchanged by this pitch and, per the spike, already
   correct: a fresh mount of P1 (were one to happen) would show the post-change values.
2. `TodoModule` builds exactly one `ListsViewModel` for the session (`TodoModule.ets:63,71`); P1
   (`ListsPage`) is mounted once and stays mounted under the `Navigation` stack while a list is
   open above it — it is never torn down and rebuilt by a P2 visit (unlike the pre-fix
   settle-across-screens `ListViewModel`).
3. The user performs a P2 action (U3: toggle, add, or delete) or confirms a P1 rename dialog. The
   underlying store mutation (`InMemoryTodoRepository.setDone`/`addItem`/`deleteItem`/
   `renameList`) reassigns `store.items` or `store.lists`, unchanged by this pitch (domain-model.md
   frozen).
4. The user returns to P1 (U4, back, or the rename dialog closing). A1/A2 (domain-model.md) is
   the fix this use case exists to specify the contract for: whatever render-layer link A1 names,
   after this step the already-mounted P1 card for the changed list reads the new `done`/`total`
   (R1/R2/R5) and/or the new name (R3), on the same frame P1 becomes visible again — not only on a
   future fresh mount of P1.
5. Card order is unaffected by a rename: `cards`' sort key is `createdAt` (unchanged, step 1), and
   rename touches only a list's `name` field, never its `createdAt` — so the fix in step 4 changes
   what a card *displays*, never the order `cards` returns them in (R6).
6. The repro device flow (shaping.md's Problem Frame, restated verbatim as this use case's R4
   fixture) exercises steps 3-4 for a toggle specifically, and is the acceptance gate for A1/A2
   together: it fails before the fix (per the spike, live on-device) and must pass after it.

## Invariants

- [INV-01] `ListsViewModel.cards` computes `done`/`total` from `store.items` filtered by
  `list.id`, and lists are sorted by `createdAt` descending — unchanged by this pitch's fix; the
  fix changes only how P1 re-renders an already-computed `ListCard[]`, never the computation
  itself (domain-model.md).
- [INV-02] A P1 card that is on screen reflects its list's current `done`, `total` and `name`
  regardless of whether P1 was freshly mounted or has stayed mounted since before the change that
  produced those values (this pitch's entire fix — the pre-fix behavior violates this only for the
  already-mounted case).
- [INV-03] Renaming a list changes only the `name` field read by a card; it never changes
  `createdAt`, so it never changes card order (unchanged domain rule, restated because R6 is a
  direct consequence of it, not a new rule this pitch adds).
- [INV-04] No new class, store field, repository method, or UI copy is introduced — the fix is
  confined to the render unit that renders one `ListCard` on P1 (domain-model.md A2's scope).

## Error Cases

None new. There is no failure branch here — a P1 card always has a well-defined `done`/`total`/
`name` to display (0 items renders `app.string.progress_none`, unchanged), and this pitch adds no
new input, no new dialog and no new network or storage call that could fail.

## System Flow

`U3 (P2 toggle/add/delete) -> N1 store mutation (reassigns store.items) -> S1 TodoStore (@Trace)`
· rename dialog (P1) `-> N1' store mutation (reassigns store.lists) -> S1` · `U4 (back) -> P1
already mounted -> N2 ListsViewModel.cards (@Computed, reads S1) -> N3 the render link A1 names
(Repeat/cardBuilder/AsyncBoundary chain, domain-model.md) -> U1 badge / card name on screen`. `S1`
is written by P2's existing, unchanged mutations and by rename; `N2` already reads `S1` correctly
on every call (confirmed by the spike: a fresh mount reads it correctly); `N3` is the single link
this use case's fix makes reflect `N2`'s current output on an already-mounted P1, which is the
use case's entire scope.
