# UC-01 — Toggle an item, guarded by a settle window

Actor: the user, on P2 List. Covers REQ-1, REQ-2, REQ-3, REQ-4, REQ-5.

## Input / Output

- Input: `itemId: string` (the id the tap landed on, from `ItemCard`)
- Output: none observable to the caller — either `ToggleItem(itemId)` runs (as retro-todo's UC-05
  already specifies) or the call is a silent no-op. `ListViewModel.onToggle` returns `void` either
  way; there is nothing for the screen to branch on.

## Steps

1. The user taps an item card (U1); `ListViewModel.onToggle(itemId)` (N1) reads `clock.now()` and
   checks the settle window (`isSettling`, domain-model.md).
2. **Outside the window**: N1 calls `ToggleItem.execute(itemId)` (N2, unchanged, retro-todo's
   UC-05) and then sets `lastToggleAt = clock.now()`, opening a new window.
3. **Inside the window**: N1 returns without calling `ToggleItem` and without changing
   `lastToggleAt` — the window does not restart on an ignored tap.
4. Whichever item toggled (step 2) still moves at once: done items sink below every open item,
   newest-created first within each group, with no reorder animation — retro-todo's `ItemOrder`
   and UC-05 Steps 3–4, unchanged and not re-specified here (REQ-4).
5. The device flow language expresses a double-tap as one `doubletap` step (A3), so R1/R2 can be
   driven and graded on the emulator rather than only through the unit test (REQ-5).

## Invariants

- [INV-01] The settle window is one named constant (`windowMs`), chosen once, not per-call.
- [INV-02] The window is screen-wide: it guards every row, including one that slides under the
  finger after a toggle, not just the row that was originally tapped.
- [INV-03] A tap outside the window always reaches `ToggleItem` — the fix never swallows a
  deliberate second tap on a different row at a normal pace (REQ-3).
- [INV-04] An ignored tap changes no state and surfaces nothing to the user (no error, no message).

## Error Cases

None new. `ToggleItem`'s own `Err(ITEM_NOT_FOUND)` (retro-todo's UC-05) is reached exactly as
before when step 2 runs; this use case introduces no error code of its own — a tap ignored by the
window (step 3) is a defined no-op, not a failure.

## System Flow

`U1 -> N1 ListViewModel.onToggle (settle-window check) -> N2 ToggleItem.execute -> N3
setDone -> S1 TodoStore.items -> N4 ItemOrder.sort -> U1` (re-sort, retro-todo's chain,
unchanged) and, for the ignored case, `U1 -> N1 (isSettling=true) -> (no-op)`.
