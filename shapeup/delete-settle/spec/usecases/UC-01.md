# UC-01 — Delete an item, guarded by the settle window

Actor: the user, on P2 List. Covers REQ-1, REQ-2, REQ-3, REQ-4, REQ-5.

## Input / Output

- Input: `itemId: string` (the id the ✕ tap landed on, from `ItemCard`, U1)
- Output: none observable to the caller — either the delete dialog opens (`ItemDeleteOpener.
  openDelete`, N2) or the call is a silent no-op. `ListViewModel.onDeleteItem` returns `void`
  either way; there is nothing for the screen to branch on.

## Steps

1. The user taps a row's ✕ (U1); `ListViewModel.onDeleteItem(itemId)` (N1) reads `clock.now()`
   and checks the settle window (`isSettling`, domain-model.md) — the same window `onToggle`
   opens, read here for the first time by delete.
2. **Inside the window**: N1 returns without looking `itemId` up in `this.store.items` and without
   calling `dialogs.openDelete` — no dialog opens, nothing deletes, and `lastToggleAt` is left
   untouched (the window neither opens nor extends on a delete) (R1).
3. **Outside the window**: N1 looks `itemId` up, and when found, calls
   `ItemDeleteOpener.openDelete(itemId, found.title)` (N2, unchanged) exactly as before the guard
   existed (R2).
4. Toggling is unaffected by this use case: `onToggle`'s own settle-window check, its write to
   `lastToggleAt`, and the sink-to-bottom reorder it triggers are untouched code, not re-specified
   here — toggle-once's UC-01 Steps 1-4 (frozen) (R3).

## Invariants

- [INV-01] The settle window stays one named constant (`SETTLE_WINDOW_MS`), shared by toggle and
  delete; this use case adds no second constant.
- [INV-02] A ✕ tap inside the window opens no dialog and deletes nothing, for any item, not only
  the one whose toggle opened the window (screen-wide, same as toggle-once's INV-02).
- [INV-03] `onDeleteItem` never writes `lastToggleAt` — only `onToggle` opens or extends the
  window; a delete inside the window leaves it exactly as it was (A2).
- [INV-04] A ✕ tap outside the window always reaches `ItemDeleteOpener.openDelete`, naming the
  item actually under that row — the guard never swallows a legitimate delete.

## Error Cases

None new. The existing "item not found" branch (`found === undefined` → no dialog opens) is
reached exactly as before when step 3 runs and the lookup misses; this use case introduces no new
error code — a tap ignored by the window (step 2) is a defined no-op, not a failure.

## System Flow

`U1 -> N1 ListViewModel.onDeleteItem (settle-window check) -> [inside window: no-op] |
[outside window: item lookup -> N2 ItemDeleteOpener.openDelete -> ConfirmDialogHost.show]`.
`S1` (the settle window) is read here, never written.
