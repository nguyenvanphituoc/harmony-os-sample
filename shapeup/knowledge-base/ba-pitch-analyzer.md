## Guidelines
- **KB-BA-001** — `entry` is an ArkUI-X cross-platform module, so any platform API missing from ArkUI-X's cross-platform list fails the build with 11706007 — test code included (UiTest `waitForComponent` and `abilityDelegatorRegistry` were rejected in the hero-todo run). Before deriving a Test Surface row that depends on a platform test API, confirm it is allowed here; when it is not, derive the row as a device or manual check and say why. _(why: a row built on a banned API becomes a test that can never compile)_  ·  from project-scan @ b8377ad (`app/.arkui-x/arkui-x-config.json5:2`); confirmed by web-research (https://gitee.com/arkui-x/docs/blob/master/zh-cn/application-dev/quick-start/platform-different-introduction.md, ArkUI-X API 24, 2026-09-15)
- **KB-BA-002** — Derive each test into the tier that can run it. Local tests (`entry/src/test`, no device, `hvigorw test -p module=entry -p coverage=false`) cover `.ts` domain and policy logic, with time and ids controlled through the `Clock`/`IdGen` ports. Instrumented tests (`entry/src/ohosTest`, module `entry_test`, device or emulator, `hvigorw onDeviceTest -p module=entry -p coverage=false`) cover ViewModels, Views and navigation; their files end in `.test.ets`, and UITest needs `hdc shell param set persist.ace.testmode.enabled 1` first. Libraries: `@ohos/hypium` 1.0.25, `@ohos/hamock` 1.0.0. The commands come from the official guides and have not yet run in this project. _(why: a row placed in a tier that cannot run it is never verified)_  ·  from project-scan @ b8377ad (`app/oh-package.json5:7-8`, `docs/index.md:716-717`); confirmed by web-research (https://developer.huawei.com/consumer/en/doc/harmonyos-guides/ide-local-test, https://developer.huawei.com/consumer/en/doc/harmonyos-guides/ide-instrument-test, DevEco 6.1.1, 2026-09-15)
- **KB-BA-003** — **Unconfirmed — verify on a device before speccing:** `docs/ui-layer.md:290,370` says the system restores the navigation stack after the process is killed, while the official Navigation reference says restoration is opt-in — `Navigation` needs `.id()` and `.recoverable(true)`, every `NavDestination` needs `.recoverable(true)` (API 14+), and non-serialisable params and custom `onPop` handlers are dropped. A spec row that relies on restore-after-kill names the opt-in it needs, and is derived as a device check: an ArkUI-X ohosTest has no compilable way to kill and relaunch the process. _(why: hero-todo's restore-after-kill criterion was never verifiable as an automated test)_  ·  from web-research (https://gitee.com/openharmony/docs/blob/master/en/application-dev/reference/apis-arkui/arkui-ts/ts-basic-components-navigation.md#recoverable14, API 24, 2026-09-15)
- **KB-BA-004** — When a spec rule says settings reset or nothing persists, check each platform API the flow calls for state it keeps on its own, and write the reset into the use case steps. Known case: `i18n.System.setAppPreferredLanguage` keeps the app language across cold start and reinstall, and setting `'default'` clears it only after the next restart. _(why: the hero-todo language selector broke its own reset-on-cold-start rule on the device)_  ·  from web-research (https://gitee.com/openharmony/docs/blob/master/en/application-dev/internationalization/i18n-preferred-language.md, API 24, 2026-09-15)
- **KB-BA-005** — Every screen's acceptance criteria cover four states — Loading, Error, Empty, Ready — derived through a `@Computed status` and rendered by `AsyncBoundary`; the first frame is always Loading, and returning to a screen refreshes it in place without going back to Loading. _(why: the team's UI contract in `docs/ui-layer.md` §2.4; a missing Empty branch only shows up in users' hands)_  ·  from project-scan @ b8377ad (`docs/ui-layer.md:326-345,769`)
