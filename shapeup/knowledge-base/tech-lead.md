## Workflow guidance
- **KB-TL-001** — At L0, before any device-bound step, check `hdc list targets` (DevEco's `…/sdk/default/openharmony/toolchains/hdc`; not on PATH). `[Empty]` → boot an emulator (`…/tools/emulator/Emulator -hvd "Pura 90" -path ~/.Huawei/Emulator/deployed`, or headless with `-start … -noWindow`), then `hdc -t <key> wait`; record `[Empty]` as an environment gap, never as a code defect. _(why: in the hero-todo run workers concluded no device was available while the emulator was attached)_  ·  from project-scan @ b8377ad (`hdc list targets` → `[Empty]`, 2026-09-15; four virtual devices deployed); confirmed by web-research (https://developer.huawei.com/consumer/en/doc/harmonyos-guides/ide-emulator-command-line, DevEco 6.1.1, 2026-09-15)
- **KB-TL-002** — At L0, confirm the machine resolves `arkui-x.dir` (in the untracked `app/local.properties`, or `ARKUIX_SDK_HOME`) and a valid `DEVECO_SDK_HOME`: a fresh clone has neither, and the build fails before compiling (hvigor `00303207` / `00303217`). After changing either, run `hvigorw --stop-daemon` (or keep `--no-daemon`). _(why: both errors occurred on this machine's first builds)_  ·  from project-scan @ b8377ad (local hvigor build log, 2026-09-10/11; `app/.gitignore:3`)
- **KB-TL-003** — At L0, the launch probe *can* install this project's unsigned HAP. `signingConfigs` is `[]` (`app/build-profile.json5:3`), so hvigor emits `entry-default-unsigned.hap` — and `hdc install -r` accepts it on the emulator, answering `install bundle successfully`. **Settled 2026-09-25**, superseding the earlier "unconfirmed" reading of the official command-line build guide, which says an unsigned HAP cannot be installed: that holds for real devices, not for this emulator target. Still record which target the run used — the guide may well be right about hardware. _(why: a launch probe that cannot install is red for reasons unrelated to the feature, and the run spent three soaks treating a solvable gap as a permanent one)_  ·  measured on target `127.0.0.1:5555` (API 24 emulator) during the retro-todo 3.9.2 soak, 2026-09-25; supersedes project-scan @ b8377ad + web-research 2026-09-15

- **KB-TL-004** — At L0, add one question to the gate block: *"Does the knowledge base name this project's build-enforced rule table as it stands today?"* `app/build-src/enforce/rule-table.ts` (rules L1–L11, 9 of them `error`) is called by `app/hvigorfile.ts:9` and `app/entry/hvigorfile.ts:11` at hvigorfile module-evaluation time, so one error-level violation fails **every** hvigor target — `assembleHap`, `test`, `onDeviceTest` alike — before any task runs. If `shapeup/knowledge-base/task-executor.md` does not carry the current rule set, or the table has changed since the provenance sha on those rules, offer `/retro --scan` before launching. Ask it and record the answer; never answer it here — the gate resolves exactly as it would without this file, and a stale KB is a reason to offer a scan, not to hold a launch. _(why: find-my-todos spent its only build round escalating on rule L6, which no worker's knowledge base mentioned; all of the code was already written and correct except two registration edits)_  ·  from project-scan @ 8ff364a (working tree)

- **KB-TL-005** — At L0, do not reach for `devecocli` (the npm `@deveco/deveco-cli` / `@ah-plugins/dsh-deveco-cli` wrapper) to make this project testable. Assessed 2026-09-25: it is a third-party wrapper over `ohpm`, `hvigor`, `hdc`, `emulator` and `hilog` — every one of which is already on disk here — and its `ui screenshot/click/swipe/layout` commands wrap `hdc shell uitest`, which this project now calls directly. It documents no test runner and no junit.xml. Adopting it would add a global npm dependency, a second binary needing its own grant, and a wrapper layer between a failure and the tool that produced it, in exchange for no capability this checkout lacks. (Huawei's **DevEco Testing** is a different product and does emit junit.xml + report.html headlessly — if CI-shaped test reporting is ever the goal, that is the thing to evaluate, not this CLI.) _(why: the on-device gap read like missing tooling for four soaks; it was a missing permission grant and an unused SDK binary)_  ·  assessed against the installed SDK and https://github.com/fz-lyle/dsh-deveco-cli, 2026-09-25
